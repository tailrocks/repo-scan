# CI

## Provenance

`.github/workflows/ci.yml` and `.github/actionlint.yaml` are generated by
`velnor-actions` from [tailrocks/velnor-new](https://github.com/tailrocks/velnor-new)
pinned to the latest main release commit (`0561601c1f71a80d16e75983124b4bd69c883bb1`).

Configuration is in `.velnor/config.toml` and release provenance in
`.velnor/release-manifest.json`.

`docs/workflows/audit.yml` and `docs/workflows/macos.yml` are maintained workflow
sources, but they are not active GitHub Actions workflows while they remain outside
`.github/workflows/`. Velnor owns the whole `.github/` tree, and the `plan` job
compares that tree with a fresh generation. Copying hand-maintained files into it
would make the generated-file check fail. Until the generator supports these jobs
or another supported activation path is adopted, only workflows in the generated
`.github/workflows/` tree run; the audit, macOS, and release jobs described below
provide no current CI checks.

## Maintained workflow sources (inactive)

`docs/workflows/audit.yml` defines an audit job. `docs/workflows/macos.yml`
defines macOS test and cross-platform release jobs. These files document desired
workflow behavior; GitHub does not discover them under `docs/`, and the current
generated CI does not execute them. Do not copy them into `.github/`: Velnor's
whole-tree generation check would reject the added files. Activation requires a
generator-supported configuration or another supported workflow integration.

## Required-check migration (human admin)

The generated workflow currently provides the `Required` job as its CI gate.
The `audit`, `macos`, and `release` jobs are not active checks in this repository,
so they cannot provide branch-protection coverage until a supported activation
path exists. Once active, update branch protection to require their exact job
names, as well as `Required`.

Branch protection settings are external to this repository and must be checked
against the jobs that are actually active on the base branch.

## Why a macOS job (§3.3.2)

The maintained macOS workflow source is intended to cover a real gap: Velnor V1
is Linux-x64-only, but repo-scan is macOS-first. The
`objc2-core-services`/`dispatch2` FSEvents backends, `libc` getfsstat paths,
and cfg-gated modules under `src/platform/` and `src/walk/` get zero coverage
from an Ubuntu run — Linux builds compile the macOS backends out. The source
workflow defines clippy and tests on `macos-15`, but that job is not active until
the source is integrated through a supported workflow path. It uses the repo's
pinned toolchain approach (`dtolnay/rust-toolchain@6bed0761…`, also used by the
audit source) and records provenance when run.

## Migration path back to real velnor (§3.5)

When the first official `velnor-actions` release lands:

1. Install the official release; commit `.velnor/config.toml` (`schema = 1`,
   `[workflow] default_branch = "main"` — required here because the repo has
   no `origin/HEAD`) plus the byte-identical official
   `.velnor/release-manifest.json`.
2. Preview: `velnor-actions generate --output-dir <fresh dir outside the repo>`
   (on macOS, not under symlinked `/tmp`), then `diff -r` against `.github`.
   Determine whether the generated workflow can express the audit, macOS, and
   release jobs, or whether Velnor provides another supported integration.
3. In-place `generate`. Do not add hand-maintained files to `.github`; activate
   the workflow coverage only through the supported integration selected above.
4. Run the required-check migration (§1 Step 6 / above).
